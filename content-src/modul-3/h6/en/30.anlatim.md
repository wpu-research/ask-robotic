### What you will learn in this lesson
- Splitting a big job into **tasks** and giving each task its own time variable
- Combining `millis`, a state machine and an interrupt in one project
- Deciding which job to do with an interrupt and which with polling inside `loop()`
- Timeout logic that puts an output into a safe state when the link is lost

### What you should know first
Lessons 26-29: blocking with `delay`, the `millis` pattern, the state machine (`enum` + `switch`) and interrupts (`attachInterrupt`, `volatile`). `tone` and `noTone` from lesson 18; `INPUT_PULLUP` from lesson 6.

### All at the same time?
A single processor does not really do jobs at the same time; it does them one after another, very quickly. If each `loop()` round takes a few microseconds and every task gets a quick look in every round, they all seem to run at the same time. The trick is that **no task ever waits**: a task either does its job or says "not time yet" and leaves.

### Task table first
Before you write the code, put the job into a table:

| Task | Trigger | Method | Its own variable |
|---|---|---|---|
| Pulse LED | 1000/250/100 ms depending on the mode | `millis` | `ledZaman` |
| Mode change | MOD button (D2) | Interrupt + flag | `modIstegi` |
| Buzzer | On/off time depending on the mode | `millis` + a small FSM | `buzzerZaman` |
| Leaving the alarm | SUSTUR (D3) or 5 s | Polling + `millis` | `modBasi` |

This way, before you write each line, you can see who affects whom. Adding a new task is just adding a new row to the table.

### Which job is an interrupt, which is polling?
An interrupt is for short events that must not be missed: when the MOD button is pressed and released once, it must not get lost even if `loop()` is busy with something else. The ISR only writes `modIstegi = true;` (and uses a 50 ms guard against bounce); the job of changing the mode is done in `loop()`. The SUSTUR button, on the other hand, can be polled with `digitalRead` every round, because the round is very short. You do not need to use interrupts everywhere.

### Reset when the mode changes
The mode is a state machine. On a transition, the `modGec()` function resets the time counters and switches the LED and the buzzer off. If you forget this, the first blink of the new mode comes at the wrong time. A small two-state (on/off) state machine is written for the buzzer too; the on and off times are given as parameters.

### What happens when control is lost?
In a remote-controlled system the link can be lost. If the last command was "run the motor", the motor may turn for ever. The fix is a **timeout**: each command renews the counter (`sonKomut = millis()`), and if no command arrives for a certain time, the output switches itself off. The rule: the safe state is "off".

### Summary
Multitasking comes from a `loop()` that checks the jobs in turn without making them wait. You write a task table and give each task its own time variable; fast events are handled with an interrupt + flag, and the rest with `millis` and a state machine. Counters are reset on mode transitions. In systems such as remote controls, a timeout that switches the output off when commands stop keeps things safe.
