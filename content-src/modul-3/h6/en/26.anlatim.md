### What you will learn in this lesson
- That the processor does nothing else while `delay()` runs (**blocking**)
- That short presses are missed if a button is only checked at certain moments
- That the length of a round decides how often "the board's eye" opens
- Why making the `delay` shorter is not a real fix

### What you should know first
`delay` and Blink from lesson 3; reading a button with `INPUT_PULLUP` from lesson 6 (pressed = LOW); the `if` condition from lesson 7; printing with `Serial.println` from lesson 9.

### What happens while the board "sleeps"?
When you write `delay(1000)`, the board only counts for one second. During that time it does not move to another line, does not read the button and does not check the serial port. This behaviour is called **blocking**. The board has not frozen; it is just carrying out the "wait" command.

### Look moments
Think about this loop:

```
on → delay(1000) → off → delay(1000) → check button
```

The button is checked only **once** per round. There are 2000 ms between two looks. A press is seen only if it happens at a look moment. If a press lasts 100 ms, its chance of being caught is about 100 / 2000 = 5%. So nine presses out of ten are missed. The button is not broken; the program does not see it.

### Text timeline
Below, a round is 2000 ms. `|` is a look moment, `#` shows the time the button is pressed:

```
time (ms):   0 ........ 1000 ........ 2000 ........ 4000
LED:         on          off          on/off
look:                                |             |
press A:       ##                                    (missed)
press B:                         ##########          (pressed at the look at 2000: caught)
```

Press A started and ended between two looks; it left no trace. Press B was counted because it covered a look moment.

### Is a shorter delay the fix?
If you write `delay(100)`, the round becomes 200 ms and the looks come more often. But two problems remain. First, there are still presses that are missed between look moments. Second, the LED's timing breaks: it no longer blinks once a second, it blinks 10 times faster. You break one thing to fix another.

### Why are two jobs hard?
Let one LED change every 1000 ms and a second one every 300 ms. With `delay`, the two waits get in each other's way; driving both correctly at the same time needs complicated calculations. Real projects (a robot's motor, a display, a button) have many jobs like this. That is why, in the next lessons, you will learn to **ask the time** instead of waiting.

### Summary
`delay()` is a blocking command: while it waits, the board does not look after anything else. If an input is only checked at the end of the round, the longer the round, the more short events are missed. Making the time shorter reduces the problem but does not solve it. The fix is code that asks "is the time up?" instead of waiting, and then carries on straight away.
