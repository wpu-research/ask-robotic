### Why "behaviours"?
As the robot's jobs grow, a single long `if / else` ladder gets tangled: adding a new job breaks the old ones. In behaviour-based control, each job is a separate, small function. The function answers only two things:

> "Should I be active right now? If yes, what do I suggest for the wheels?"

A behaviour does not drive the motors itself; it only returns a **suggestion**: an `aktif` (active) flag and two wheel speeds.

### The arbiter
The part that collects the suggestions and picks one is called the **arbiter**. The simplest arbiter works like this: go through the behaviours in priority order and apply the suggestion of the first active behaviour.

| Priority | Behaviour | Condition for being active |
|---|---|---|
| 1 | `KAC` (escape) | Front distance below 25 cm (until it goes above 60 cm) |
| 2 | `CIZGI` (line) | One of the line sensors sees the line |
| 3 | `DOLAS` (wander) | Always (default) |

When you write `enum Davranis { KAC, CIZGI, DOLAS }`, the number order becomes the priority: KAC = 0 comes first. The arbiter starts from 0 with a `for` loop and stops with `break` at the first `aktif` behaviour. So if `KAC` is active, whatever `CIZGI` suggests is ignored.

`DOLAS` always being `aktif` is a deliberate design: it is the last safety net, saying what the robot should do when no behaviour is active.

### Two thresholds: hysteresis
If `KAC` started at 25 cm and also ended at 25 cm, then while the robot was turning it would let go as soon as the distance rose just above 25 cm, drive forwards, drop below 25 again and jitter. The solution is two thresholds: start at 25 cm, end when it goes past 60 cm. For this, the behaviour has a small memory (the `kaciyor` (escaping) variable).

### What happens if you change the order?
The priority order is a "list of values". If you put not bumping into things at the top, the robot will be timid but safe. If you put `DOLAS` at the top, the others never run again, because the arbiter always picks the first behaviour. Adding behaviours is easy: you write a new function and put it in the order, without touching the others.

### Summary
In behaviour-based control, each job is a behaviour and only returns a suggestion. The arbiter picks the first active behaviour according to the priority order, and only that one drives the motors. In behaviours like `KAC`, two thresholds prevent jitter. Setting up the priority order correctly decides what the robot cares about first.
