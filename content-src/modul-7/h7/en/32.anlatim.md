### What you will learn in this lesson
- Why a fluent explanation of code does not have to be correct
- How to sort a claim, by looking at the code, into "matches", "contradicts" or "not in the source"
- How to test an explanation by predicting the output yourself
- How edge cases such as an empty list lead to errors

### What you should know first
Lesson 31: the workflow for writing code with AI and the principle "do not believe it without running it". It is enough to know that a model can make up details. You are expected to have seen the `for` loop and the `len()` function in Python.

### Fluency is not correctness
When a language model explains code, it also chooses the next word by what is likely. An explanation can be written in good, confident language and still be wrong. The seven claims used in this lesson are **hand-written examples**; they are not real model output. The aim is to learn what to look at before accepting an explanation.

### Three kinds of claim
```
Matches the source      The code really does this.
Contradicts the source  The code does the opposite.
Not in the source       Nothing like this appears in the code at all.
```
The sneakiest kind is the third. The sentence "It saves the result to a file" looks harmless, but if there is no file operation in the code, it is a made-up detail. The way to compare is simple: for every verb in the claim, go back to the code and look for the line where that verb happens. If you cannot find the line, the claim has no support.

### Predict the output yourself
Instead of trusting the explanation, run the code by hand:
```
def toplam_ort(liste):
    t = 0
    for x in liste:
        t += x
    return t / len(liste)
print(toplam_ort([5, 7, 9, 11]))
```
The total is 32, the number of elements is 4, and the result is 8.0. In Python the `/` operator gives a decimal result even between whole numbers; the screen shows `8.0`, not `8`. If a claim says "it prints 32", you catch the contradiction by noticing that 32 is the total and that the function divides and returns the result.

### Edge cases
If you give the average function an empty list, `len([])` is zero and a division-by-zero error (`ZeroDivisionError`) happens. An explanation that says "it returns 0 if it is empty" contradicts the code, because there is no `if` in the code doing that job. Trying edge cases (an empty list, a single element, a very large number) brings hidden assumptions like these to light. There is also an indentation detail: if the `return` line stays inside the loop, the function stops at the first element and the result changes completely.

### Summary
A model speaks fluently, but it does not check the code. Sort claims, by looking at the code, into matching, contradicting or not in the source. Predict the output by hand, try edge cases and, if you can, back it up with a test. That way you will not be fooled by a made-up detail.
