### A coding tool is an agent
Coding assistants that run in the terminal use exactly the loop you saw in week 6: read the file, make a plan, change it, run the test, look at the result, fix it. The **tools** for reading files, editing and running commands are real. Which tool to call and when, however, is decided by a **language model**. The model works with probabilities; so a step that looks fluent and confident can still be wrong.

### The six-step workflow
```
1. Goal        What do I want? Which files will be affected? What must not break?
2. Plan        Have the plan written first, read it, fix wrong assumptions.
3. Small step  Break the big job up. Instead of one 240-line change,
               6 steps x 40 lines.
4. Test        Define the behaviour with a test and run it.
5. Review      Read the change line by line.
6. Record      Save every working step with a small commit.
```
The benefit of small steps is this: when something breaks, the culprit is within 40 lines, not 240. A commit keeps the way back open.

### Made-up code and weak tests
A model can write a function that does not really exist in a very natural way. For example, Python's `statistics` module has `mean` for the average; there is no `average`. If the model writes `statistics.average(...)`, the code gives an error on the first run. That is good news: running it catches the error. The real danger is code that runs wrongly without giving an error.

The typical form of this is a weak test:
```
def buyuk(a, b):
    return a
assert buyuk(7, 3) == 7
print("test geçti")
```
The test passes (it prints `test geçti`, "test passed"), but the function always returns the first number (`buyuk` means "bigger"). The sentence "The tests passed" only says that the **tests that were written** passed; it does not guarantee that the code is right. A good test includes both expected cases and edge cases (for example `buyuk(3, 7)`).

### Permissions and secret information
A tool is as useful as the permission you give it, and can do as much damage as the permission you give it. Ask for approval on risky commands such as deleting files or accessing the network. Do not write passwords and keys into the code or into your request. Do not take ownership of code you do not understand: the person responsible is the one who accepts it.

### Summary
A coding AI is an agent: the tools are real, the decisions are the model's. A safe workflow is made of the steps goal, plan, small step, test, review and record. The model can make up functions, and weak tests can approve wrong code; that is why running and reading the code is your job. To limit the risk, give the tool the least privilege.
