### What you will learn in this lesson
- How to build your own eval set from start to finish
- How to write an honest, short eval report
- Why the result of a small set should be viewed with caution
- Why you run the eval again after changing the system

### What you should know first
Lessons 16-19: evals and accuracy (16), writing balanced cases (17), per-label recall (18), edge cases and data leakage (19).

### The project is an engineering cycle
You will bring together what you learned this week in a single flow:

```
1. Write the cases (balanced, varied, no repeats)
2. Run the eval
3. Look at the accuracy and the per-label results
4. Group the mistakes and find their cause
5. Suggest an improvement (and when it changes, go back to 2)
6. Write the report
```

The aim of the project is not to defend the system, but to expose its weak spots. A good test engineer does not say "it works"; they say "it doesn't work in these cases".

### The size of the set and confidence
Ten cases is a very small set. With 10 cases, each case moves the accuracy by 10 points: 8 / 10 = 80%, 7 / 10 = 70%. In a set of 100 cases, the same single case moves it by only 1 point. That is why, for the result of a small set, you cannot say "definitely 80%"; you say "80% on these 10 cases". Real eval sets can contain hundreds or thousands of cases.

### What does a good report say?
The report has four parts:
- **Result:** the overall accuracy and the per-label recall.
- **Mistakes:** which cases were got wrong and why (for example sarcasm, or the word `hata` (error) being in the negative list in the sentence `Hata yok` (No errors)).
- **Idea:** one step for improving the system (a word list or a rule change).
- **Limit of confidence:** is the number of cases enough, is the set balanced, are the tuning set and the measurement set separate?

### Measure again when you change something
Adding a word can fix one mistake while breaking another case. That is why you run the eval from the start after every change; this is called a **regression test**. If you want to measure an improvement, you should compare the old and new results on the same cases, and report the final number on a separate set.

### Summary
The project is a cycle of write cases, measure, group the mistakes, improve and report. The result of a small set is not certain; saying this clearly in the report is honesty. Run the eval again every time you change the system, and keep the tuning set and the measurement set separate.
