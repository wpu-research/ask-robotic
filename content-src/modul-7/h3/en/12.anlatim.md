### People read, programs parse
A person understands the sentence "I think this comment is positive and about the robot lesson"; a program does not. This is the form a program can read (keys `duygu` = sentiment, `konu` = topic):
```
{"duygu": "olumlu", "konu": "robot dersi"}
```
**JSON** is an orderly data format made of key-value pairs. Keys and text values are written in **double quotation marks**, items are separated by commas, and no comma is put after the last item.

### A prompt that asks for JSON
A good request contains: the name of the format ("JSON"), the key names (`duygu`, `konu`), an example output and the constraint "write nothing except JSON". The key names in the example must be the same as in the instructions; if one says `duygu` (sentiment) and the other `his` (feeling), the model cannot know which one to choose.

### Why is validation a must?
The model writes using probability (lessons 4 and 6). Most of the time it produces proper JSON, but sometimes it adds "Here is the result:" in front, misses a quotation mark or forgets a key. The code below gives an error in the first case:
```
const veri = JSON.parse(yanit)   // throws an error if yanit is not valid JSON
if (!("duygu" in veri) || !("konu" in veri)) {
  // one of the expected keys is missing: try again or give an error
}
```
Validation has two layers: first, is it valid JSON; then, are the expected keys there. If it fails, the app tries again or reports the error to the user. Some services offer features that force the output to fit a schema; the logic is still the same: don't trust the model, check.

### What do you see in the Workshop?
The tool in the Workshop judges only the **prompt** you write: do "JSON" and the key names appear, is there an example. It does not produce a model answer, and it does not validate that answer. The validation code is a separate step, and in a real app you apply it to the model's reply.

### Summary
Programs want orderly data; JSON is a common format for it. A prompt should contain the format name, the key names, an example and a ban on extra text. The model usually follows this request, but there is no guarantee: always parse the output and check the keys. A failed validation is not a bug but a normal situation, and it should be planned for.
