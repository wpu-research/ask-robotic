### Project: a prompt someone else can use too
Task: a prompt that summarises the robot club's announcements for 13-year-old students. Goal: when someone else reads this prompt, they should be able to understand what each part is for.

### A six-part skeleton
| Part | Example sentence |
|---|---|
| Role | You are an experienced robotics club mentor. |
| Task | Summarise the announcement below. |
| Context | The readers are 13 years old; the aim is that they don't miss the meeting. |
| Example | Announcement: We meet on Tuesday. Summary: - There is a meeting on Tuesday. |
| Format | Write the summary as at most 3 bullet points. |
| Constraint | Do not add information that is not in the announcement. |

### Faithfulness to the source
The biggest risk of a summariser is adding information that is not in the announcement (for example making up the time). The constraint "do not add missing information" tells the model this but does not guarantee it; the model may still make things up. In lesson 36 you will learn to catch made-up information. To make the prompt reliable, you test it by comparing the output with real announcements.

### Simplifying
Every sentence should do a job. Adjectives such as "Please write a really nice and amazing summary" give the model no information about format, audience or limits. If taking a sentence out does not lower the quality, that sentence is unnecessary. But to see this you need to try it: do not take anything out or add anything without measuring.

### Design note
Write it in three or four sentences: why this role, why this example, why this format? The note is both a record for yourself and a document that lets someone else understand your prompt.

### What happens in the Workshop?
The Workshop tool scores your prompt using rules; it does not produce a model answer. 90 points means "the required parts are there". It is not guaranteed that you will get results of the same quality on a real model.

### Summary
The project brings together all the week's skills: the six parts, an example, a format, a constraint, simplifying and justification. A high score alone does not count as proof; the proof is tests with real announcements. The design note lets you explain your decisions to others.
