### What you will learn in this lesson
- What tool use is, and why the model calls a calculator
- How a tool call is written: `arac(girdi)` (tool(input))
- How a tool's result (the "observation") is carried to the next step with `$1`
- That a tool error is not a crash but an observation to read

### What you should know first
From lessons 1-25 of this module, especially these: the idea that a language model works by predicting words (Lesson 4), and the idea that a model can bring in information from outside (RAG, Lessons 23-25). The four basic operations are enough.

### Why does the model not calculate "from its head"?
A language model predicts the next piece. On small operations it is often right, but on a multi-digit multiplication or on up-to-date information it can be wrong; there is no guarantee that it is right. The fix is to hand the job to a **tool** that knows how to do it. A **tool** is an ordinary program that the application runs: a calculator, a search, reading a sensor, and so on.

### How does a tool call work?
1. The application gives the model a list of tools: name, what it does, which input it takes.
2. In a step, the model says "I want to call this tool with this input". The model does not run the tool itself; it only produces a request.
3. The application **really runs** the tool and gives the result back to the model. This result is called an **observation**.
4. The model looks at the observation and carries on, or gives the answer.

In the workshop this third step is real: the calculator is an expression parser that only accepts numbers and operations. The first step, however, is not a real model. You write the tool calls as a script; so the "model step" is a simulation, and it is labelled that way on the screen.

### Call format and chaining
A call has the form `arac(girdi)`:

```
hesapla(12*7)
hesapla($1+16)
bitir($2)
```

`$1` is the result of the first step (84), `$2` that of the second (100). `bitir(...)` ("finish") closes the job and gives the answer. The calculator knows the order of operations: `hesapla(2+3*4)` gives 14, not 20.

### An error is an observation too
The call `hesapla(1/0)` does not crash the program; an error observation saying "division by zero" comes back. A good agent reads this observation and tries something else. Careful: in the workshop the error text of a failed step is also carried with `$n`, so the next step may have received an error text instead of a number.

### Summary
In tool use, the model proposes a decision, the application runs the tool and the result comes back as an observation. Handing exact jobs such as calculations to a tool is more reliable than trusting a guess. Calls have the form `arac(girdi)`, and results are carried with `$1`, `$2`. An error is an observation too; it should not be passed over without a look.
